# CLOUDLE | 요구사항 정의서(SRS)

> **Wrap the Earth in Care. Make It Greener, One Thing at a Time.** — 지구를 다정히 감싸고, 물건 하나부터 조금씩 더 푸르게.

**상태:** 기획안 v0.1 · **기준:** 첨부 「AI 코어 프로젝트 2회차 요구사항정의서」 · **우선순위:** MoSCoW

## 1. 시스템 범위

- **목적:** 생활용품을 재사용·수리·배출할 때 필요한 근거 자료를 검색해 행동 가능한 안내 제공.
- **사용자:** 비회원(지역·품목 선택/검색·질의응답), 운영자(자료 출처·색인·오류 관리). 회원가입은 비필수.
- **입력:** 품목/모델명, 자연어 질문, 지역, 처리 목적. 사진 인식은 심화 후보이며 MVP는 텍스트·카드 선택 중심.
- **출력:** 수리·재사용·배출에 관한 **문서에 확인된 조건만**, 주의사항, 근거 번호/원문 URL, 처리 상태. 지구본의 환경 수치는 데이터 시각화로 별도 제공.
- **제외:** 직접 중고거래·결제·실시간 시세 보증·물품 상태 자동 인증·세계 모든 지역의 배출 규칙 보장.
- **용어:** RAG(근거 검색+생성), RAG 1(항목 메타데이터), RAG 2(외부 문서), 청크(문서 조각), Top-k(검색 근거 수), MMR(중복을 줄이는 다양성 검색).

## 2. 요구사항 적용 원칙

- **PDF 필수 F2001~F2012는 전부 Must.** 내용 삭제·완화 없이 CLOUDLE 용어로 구체화한다.
- PDF 심화 **F2013~F2016은 선택**; 선택했으면 심화 검증까지 수행한다.
- **NF2001~NF2007은 필수 비기능 점검 항목**으로 관리한다.
- 새 기능은 `C01~`로 번호를 분리하고, MoSCoW의 Must/Should/Could/Won't를 적용한다.

## 3. 기능 요구사항(과제 필수: 변경 불가)

| ID | 기능(입력 → 처리 → 결과) | 완료 기준 | MoSCoW |
|---|---|---|---|
| **F2001** | 품목 100건 이상 로드 → 이름·별칭·재질·분류·설명으로 **항목당 색인 텍스트 1개** 구성 | 실제 항목 수·텍스트 샘플 출력 | Must |
| **F2002** | 품목 텍스트 임베딩 → ChromaDB **`item_meta`** 컬렉션 저장 | 항목수=색인수, 재실행 시 중복 없음 | Must |
| **F2003** | 선택 품목·질문 → **프롬프트 1**로 외부 문서 검색어 JSON 추출 | 품목 자체를 다루는 검색어 포함, 파싱 가능 | Must |
| **F2004** | 출처 검색 → **프롬프트 2**가 후보 선별 → 본문·원문 위치 기록 | 품목 직접 설명 문서 우선, 검색어 수집 캐시 | Must |
| **F2005** | 수집 문서 청킹·임베딩 → 별도 **`evidence_docs`** 컬렉션 저장 | 제목·URL·관련 item_id·청크ID 존재, 크기/중복 설정 가능 | Must |
| **F2006** | 선택 품목의 메타데이터 반드시 포함 + 관련 외부 청크 의미 검색 → 병합·중복 제거 | 두 출처 유형 구분, Top-k 조절 가능 | Must |
| **F2007** | LangGraph `retrieve → generate` + **프롬프트 3**로 검색된 근거만 사용 | 자료에 없는 결론은 “문서에서 확인되지 않음” | Must |
| **F2008** | 답변 근거 번호와 실제 인용 문서의 제목·출처 제공 | `[근거 n]`과 화면의 실제 사용 근거 1:1 일치 | Must |
| **F2009** | 품목 선택 → 품목별 채팅 질문/답변 | 품목 A/B 전환 시 대화 내역 혼합 방지 | Must |
| **F2010** | 도메인 특화 기능 **‘다음 선택’** 제공 | 수리·재사용·배출 안내와 출처 제시 | Must |
| **F2011** | 자연어 조건(예: “배터리 내장 생활가전”) → 후보 검색·조건 재선별 | 일치 품목만 표시, 카드 선택 후 질문 연계 | Must |
| **F2012** | 수집·검색·생성 진행 상태 및 색인 없음·키 누락·근거 없음 오류 안내 | 해당 상황 재현 시 적절한 안내 표시 | Must |

> RAG 1(메타데이터)과 RAG 2(외부 문서)는 **데이터 출처와 색인 대상이 서로 다르다.** 외부 문서는 선택된 품목 자체를 다루는 자료를 우선 포함하고, 중복 청크는 제거한다.

## 7. 핵심 유스케이스(UC-01)

1. 방문자가 로그인 없이 품목 검색에서 `보조배터리`를 선택한다.
2. 선택적으로 `서울`과 `배출`을 고르고 카드를 통에 넣는다.
3. 서버가 품목별 메타데이터를 확정하고 프롬프트 1로 검색어를 추출한다.
4. 캐시 확인 후 허용된 문서 출처에서 후보 수집 → 프롬프트 2로 선별 → 청킹·색인한다.
5. `retrieve`가 품목 메타데이터와 배출 지침의 관련 청크를 병합한다.
6. `generate`가 문서에 확인된 부분만 답하고 `[근거 1]` 등을 부여한다.
7. 화면은 주의사항과 인용 원문을 함께 제시하고 후속 질문을 받는다.

**대안 흐름:** 데이터 없음/키 누락/문서 출처 부족 시 오류 안내·재시도·'확인 불가' 표시. 리콜 여부, 배터리 상태 등은 문서·실물 확인 없이 단정하지 않는다.

## 8. 검증·인수 기준

- [ ] **1일 차 16시:** 실제 품목 **100건 이상** 로드, 각 품목 외부 설명 자료의 확보 가능성 및 이용조건 확인(미달 시 PDF 지침에 따라 영화 팩).
- [ ] F2001~F2012 **전체 통과**, 표의 완료 기준별 화면/로그 캡처.
- [ ] NF2001~NF2007 점검 및 결과 기록.
- [ ] 색인 두 번 실행해 중복 없음, chunk 크기·Top-k 변경 테스트.
- [ ] 근거 있는 질문 / 근거 없는 질문 / 조건 필터 / 품목 전환 / 외부 API 실패 테스트.
- [ ] **선택** 심화 적용 시 F2013~F2016 중 해당 기능 검증; F2015 선택 시 대표 질문 5개 비교.
- [ ] 체크리스트 `통과/실패/미확인` 기록, 셀프 및 상호 점검, 근거자료 캡처 제출.
- [ ] **최종 산출물:** 요구사항 정의서·RAG 파이프라인 설계문서·구현 코드·검증 결과·README.

## 9. 제약·가정

- 개발 기본은 과제 명시 **Python 3.10+, Streamlit, ChromaDB, LangChain/LangGraph**. 직접 3D UI를 선택하면 HTML/CSS/JS와 별도 서버 API 연동 검토.
- 외부 데이터 접근 권한과 이용조건은 각 제공기관이 결정한다. 웹사이트 공개 사실만으로 대량 저장·임베딩이 허용되지는 않는다.
- **분리배출 API는 서울 지역 범위**로 한정되므로, 다른 지역은 확인된 자료가 없으면 해당 규정 제공을 보류한다.
- 중고 가격·수리 가능성은 상태/견적을 요하므로 RAG만으로 확정하지 않는다.
- 환경 통계는 관측값의 시각과 통계 기준연도를 항상 제시한다.
